Ideation: xz 工具调用优先采用 Scene-Shell

日期2026-07-17
话题xz-tools-scene-shell
聚焦调用 xz 系列工具时候，优先采用 Scene-Shell
模式repo-grounded

📌 Grounding Context

核心缺口：xz 工具（xz_calendar / xz_notes）目前零 Scene-Shell 集成。src/capabilities/tools/xz.js 直接 spawn CLI，返回工具信封 JSON（{ok, stdout, ...}），无后处理、无 surface 投影。Agent 收到的是 raw stdout 字符串（或嵌在字符串里的 JSON），需要自己 parse 再用文字描述给用户。

三个已有先例模式（xz 可直接参照）：

  • 模式 A — core 直接投影（天气）：index.js:816-838 projectWeatherSurfaceForTurn，确定性查询结果由 core 直接投影成 kind:'weather' surface，不经 Agent。
  • 模式 B — job 咽喉点投影（软件安装）：software-install-scene.js 挂在 updateJob 咽喉点，把异步 job 状态翻译成 kind:'progress' surface。
  • 模式 C — 工具内挂 choice+confront（安全确认）：executor.js:1120-1164 execSetSecurity 用 kind:'choice' + intent:'confront' + data.pending 做写操作确认。

kind 词汇表现状：scene-shell 注册了 text/metric/image/choice/weather/progress/selfcheck/awakening/stack/row/col。缺 list/table 和 form——协议（SCENE-PROTOCOL.md §6）定义了 form 但 shell 未实现（kinds/index.js 无 form.js）。

web 行业对标：Google A2UI（声明式 JSON-as-UI）、CopilotKit（per-tool render 映射）、SimplePractice/TherapyNotes（临床 EMR 把列表/表格当一等公民）。

🧭 Topic Axes

  • 轴 A：呈现粒度 — 单个操作结果投影 vs 复合面板（今日排班+缴费+待办聚合）
  • 轴 B：交互模式 — 纯展示（只读投影）vs 交互决策（选项选择/确认）vs 结构化输入（表单）
  • 轴 C：数据流路径 — core 直接投影 vs Agent 自主声明 vs 投影层翻译
  • 轴 D：场景类型 — 查询类 vs 写操作类 vs 长任务类

🏆 Ranked Ideas

  • #1 xz-scene.js 投影层
  • #2 临床工作台 surface
  • #3 写操作 confront 确认流
  • #4 xz context block 加 ui_set 引导
  • #5 补 list/table kind
  • #6 脱敏投影
  • #7 工具不可用引导卡

1xz-scene.js 投影层（per-command 映射表）

建一个独立的投影层文件 src/capabilities/tools/xz-scene.js，内含一张 per-command → surface 模板映射表。xz_calendar command="today" → 今日排班 surface 模板；command="appointment list" → 列表 surface 模板。executor 调完 CLI 后，按表把 stdout 解析成结构化 data 投影成 surface。这是 CopilotKit 的 render-per-tool 模式。

xz_calendar({command:"today"}) │ ├─► spawn CLI → stdout (JSON) │ ▼ xz-scene.js 映射表 command="today" → { kind:"stack", data:{children:[ {kind:"text", data:{title:"今日排班", body:"..."}}, {kind:"metric", data:{label:"待缴费", value:3}} ]}, intent:"inform" } │ ▼ sceneStore.set("xz-today-{date}", surface) → /scene WS → shell 投影
轴：C（数据流：投影层翻译）
basis：direct: software-install-scene.js 已是独立投影层先例；executor.js:1124 注释确认 Scene 无专用领域 kind；external: CopilotKit render-per-tool 模式
rationale：把「CLI 输出格式」和「surface 呈现」解耦——xz CLI 升级不影响 UI，UI 升级不影响 CLI。新增子命令只需加一行映射。这是整个 ideation 的基础设施，其他想法都依赖它。
downsides：需要为每个 xz 子命令写解析+映射逻辑；CLI 输出格式变化时映射表要同步更新。中等工程量。
confidence：85% complexity：Medium

2「咨询师临床工作台」持续在场 surface

不是逐次查询返回单张卡，而是一个持续在场的「临床工作台」surface——今日排班 + 待缴费 + 待编译笔记聚合在一个 stack 面板里。core 在 TICK 心跳时自动刷新（仿天气 ambient 投影），随状态 morph 更新。咨询师早上打开 Jarvis 就看到「今日全貌」，零交互。

┌─── 咨询师工作台（intent: ambient，持续在场）───┐ │ │ │ 📋 今日排班 (3) 💰 待缴费 (2) │ │ ┌─────────────┐ ┌──────────────┐ │ │ │ 09:00 王XX │ │ 李XX ¥800 │ │ │ │ 11:00 陈XX │ │ 张XX ¥600 │ │ │ │ 14:00 刘XX │ └──────────────┘ │ │ └─────────────┘ │ │ │ │ 📝 待编译笔记 (1) ⚠ 临床提醒 │ │ ┌─────────────┐ 上次会期未确认知情同意 │ │ │ 张XX 06-15 │ │ │ └─────────────┘ │ └────────────────────────────────────────────────────┘
轴：A（复合面板）+ C（core 自动）+ D（查询类）
basis：reasoned: 天气已有 ambient 自动投影先例（index.js:816）；TICK 心跳机制天然适合定时刷新；external: 医院 HIS/EMR 临床看板范式——持续在场的多区域仪表盘
rationale：心理咨询工作流天然多维并行（预约→会面→记录→结算），HIS 看板范式经过验证。这是从「响应式工具调用」升级到「主动式仪表盘」的旗舰特性。
downsides：需要 core 定时调 xz CLI 刷新（CLI 负载+延迟）；surface 过大可能抢焦点（需克制 intent=ambient）；CLI 不可用时看板空白需优雅降级。
confidence：75% complexity：High

3写操作 confront 确认流（仿 set_security）

所有 xz 写操作（创建预约、缴费登记、笔记确认）走 confront choice 确认卡片。Agent 收集完信息后，弹一张「预约摘要：来访者 XX / 时间 / 时长 / 缴费状态」的 kind:'choice' + intent:'confront' 卡，用户确认后才真正写入 CLI。pending 变更存在 data.pending 里，用户确认后 scene intent handler 取出 apply。完全复用 executor.js:1142 的 set_security 机制。

轴：B（交互决策）+ D（写操作类）
basis：direct: executor.js:1120-1164 set_security 用 choice+confront+pending 做安全确认；external: 航班/酒店预订确认流——高代价操作前的视觉确认
rationale：心理咨询预约创建错误（时间/来访者搞混）的代价比航班改签更高——临床关系、计费、排班连锁影响。confront 级确认是临床安全要求。
downsides：每个写操作多一步确认可能降低高频操作的流畅度；需区分「需要确认」和「低风险直接执行」的边界。
confidence：90% complexity：Low

4xz context block 加 ui_set 引导（最小改动杠杆）

在 capability-registry.js:218-228 的 xz context（函数式 lazy 求值）里加一段引导文本，教 Agent「调完 xz_calendar today 后用 ui_set 投影成 stack/text」。仿 WEATHER_CONTEXT_BLOCK（:84-95）写一段 XZ_CONTEXT_BLOCK。这是不改架构、不补 kind的最小改动路径。

轴：C（数据流：Agent 自主声明）
basis：direct: capability-registry.js:84-95 WEATHER_CONTEXT_BLOCK 教 Agent 调 ui_set 的完整先例——字段映射、调用示例、去重约束
rationale：最低成本、最快见效。xz context 当前只教 CLI 用法零 scene 引导，加一段文本即可让 Agent 尝试投影。但单独使用可能不够（Agent 不一定遵守、投影质量不稳定）——适合作为 #1 投影层的补充而非替代。
downsides：Agent 可能不遵守引导规则；投影格式不稳定（模型可能拼出不规范的 surface data）；不如 core 直投可靠。
confidence：70% complexity：Low

5补 list/table kind（全局杠杆）

scene-shell 的 kind 词汇表缺 list/table——xz 的核心场景（预约列表、来访者列表、缴费明细）全是列表/表格数据，现在只能用 stack+text 凑。补一个 list kind（支持表头+行+状态色），xz 和未来所有列表类工具都受益。

轴：A（呈现粒度）
basis：external: SimplePractice/TherapyNotes 等临床软件把列表/表格当一等公民；CopilotKit dashboard 也是；direct: kinds/index.js:27 REGISTRY 确认无 list/table
rationale：kind 词汇表扩展是全局杠杆——不只是 xz，hotspot/worldcup/任何列表类数据都受益。stack+text 凑列表是临时方案，语义和动画都不理想。
downsides：新增 kind 需要实现 render/enter/exit/morph 四段+CSS；需更新 SCENE-PROTOCOL.md 词汇表。但这是一次投入永久受益。
confidence：80% complexity：Medium

6脱敏投影（隐私保护）

心理咨询数据高度敏感。surface 里来访者用代号（C-001）而非真名，真实姓名只在 Agent 内部上下文。类比 xz-notes 已有的脱敏（redaction）概念。屏幕可能被旁人看到，脱敏投影保护来访者隐私。

轴：A（呈现粒度）+ D（场景类型）
basis：direct: schemas/xz.js:48 xz_notes schema 含 "safety consent / redaction set / 脱敏"——临床脱敏是已有概念
rationale：临床合规——咨询师在公共场合/有人进入时，屏幕不应暴露来访者身份。xz_notes 的 redaction 机制已存在，surface 投影应与之对齐。
downsides：代号→真名的映射需要管理；用户可能觉得代号不直观。可做开关（设置里「脱敏模式」）。
confidence：65% complexity：Low

7工具不可用引导卡（ENOENT 降级）

日志显示 xz-notes 曾 ENOENT（CLI 不在 PATH）。翻转「工具依赖 CLI」为「surface 不依赖 CLI 成功」：即使 CLI 不在，Agent 仍可用 ui_set 展示「检测到 xz 工具未安装」的 choice 卡（intent:'confront'），引导用户配置，而非纯文字报错。

轴：D（场景类型：错误处理）
basis：direct: 运行日志——xz-notes spawn ENOENT，Agent 只能用文字报错
rationale：工具不可用时视觉引导（配置卡片）比文字错误信息更友好。这是边缘场景但 UX 提升明显。
downsides：边缘场景，投入产出比一般。可作为 #1 投影层的附带功能。
confidence：60% complexity：Low

✂️ Cut Ideas（被淘汰的想法及原因）

F1-1. xz 输出是「工具信封 JSON 包裹 stdout」（淘汰——这是问题描述不是想法）

淘汰原因：这是 grounding 发现的现状描述，不是可执行的想法。它已被 #1（投影层）和 #4（context 引导）作为问题前提吸收。保留在 Grounding Context 里更合适。

F1-2. Agent 不知道屏上有什么（淘汰——已被 #4 吸收）

淘汰原因：这是「xz context block 缺 ui_set 引导」的另一种表述，已被 #4 完全覆盖。重复保留无增量价值。

F2-2. stable surface id 自动生成（淘汰——实现细节非想法）

淘汰原因：自动 id 生成（xz-today-{date}）是 #1 投影层的实现细节，不构成独立的方向选择。属于 ce-plan 层面的技术决策。

F2-3. 查询结果阅后即焚 TTL（淘汰——与 #2 工作台矛盾）

淘汰原因：TTL 自动退场与 #2「持续在场工作台」直接矛盾——工作台需要持久在场，TTL 会把它收掉。TTL 适合单次查询卡，但 #2 的复合面板范式更优。如选 #1 单卡路径，TTL 可作为实现细节保留。

F3-3. Agent 不需要看完整 CLI stdout（淘汰——风险过高）

淘汰原因：「投影给用户但不全量返回 Agent」改变了工具结果语义，可能导致 Agent 基于不完整信息做错误决策（如用户问「今天第三个预约是谁」时 Agent 不知道）。manifest 回注设计已有摘要机制，不需要截断工具结果。风险/收益比不划算。

F4-2. 补 form kind（降级——依赖过重）

淘汰原因（降级为 deferred）：form kind 确实缺失，但创建预约的表单需求可以用 #3 的 confront choice 确认流替代（Agent 逐字段收集→确认卡）。补 form kind 工程量大（需完整实现 render/submit/字段验证），收益场景窄。作为 deferred——如果未来需要复杂多字段表单再补。

F5-2. Git CLI→IDE 可视化双通道（淘汰——已由 #1 覆盖）

淘汰原因：「CLI 保留给脚本，surface 给交互」的双通道理念已被 #1 投影层隐含实现——投影层就是那个「交互通道适配器」。作为独立想法无增量。

X2. 投影层+映射表+context 三件套（淘汰——合并到 #1+#4）

淘汰原因：cross-cutting 综合 X2 是 #1 + #4 的组合表述，不是新方向。已在 ranked list 里通过 #1 和 #4 并列体现。
